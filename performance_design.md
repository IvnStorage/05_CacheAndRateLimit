# Performance design

## 1. Что оптимизируется?

Основная нагрузка возникает на чтении данных и авторизации (по моим предположениям).

Часто вызываемые операции:

- поиск книг;
- получение списка выдач пользователя;
- авторизация.

Медленные места:

- повторные запросы к PostgreSQL;
- поиск книг по названию или автору;
- получение выдач пользователя;
- частые запросы на login.

Поэтому цель оптимизации не меняя логику снизить количество лишних обращений к базе и ограничить слишком частые запросы на авторизацию.

## 2. Кеширование

Для кеширования используется Redis.

Выбрана стратегия Cache-Aside:

1. API сначала проверяет данные в Redis.
2. Если данные есть, возвращает их из кеша.
3. Если данных нет, обращается к PostgreSQL.
4. После этого сохраняет результат в Redis с TTL.

Этот подход выбран потому, что он простой и подходит для чтения данных, которые часто запрашиваются повторно.

## 3. Что кешируется?

### `GET /api/v1/books/search`

Кешируется результат поиска книг.

Пример:

```http
GET /api/v1/books/search?title=War
```

TTL: 60 секунд.

Кеш сбрасывается при:

- создании книги;
- создании выдачи;
- возврате книги.

Нужно так как после этих операций результат поиска может измениться.

### `GET /api/v1/users/{userId}/loans`

Кешируется список выдач пользователя.

Пример:

```http
GET /api/v1/users/1/loans
```

TTL: 30 секунд.

Кеш сбрасывается при:

- создании выдачи;
- возврате книги.

TTL меньше, потому что выдачи меняются чаще, чем общий список книг.

## 4. Проверка кеша

Проверка поиска книг:

```powershell
curl.exe -i "http://localhost:8080/api/v1/books/search?title=War"
curl.exe -i "http://localhost:8080/api/v1/books/search?title=War"
```

Результат:

```text
первый запрос: X-Cache: MISS
второй запрос: X-Cache: HIT
```

После создания новой книги кеш был сброшен. Следующий запрос снова вернул `X-Cache: MISS`, затем повторный запрос вернул `X-Cache: HIT`.

Проверка выдач пользователя:

```powershell
curl.exe -i "http://localhost:8080/api/v1/users/1/loans"
curl.exe -i "http://localhost:8080/api/v1/users/1/loans"
```

Результат:

```text
первый запрос: X-Cache: MISS
второй запрос: X-Cache: HIT
```

## 5. Rate limiting

Rate limiting добавлен для:

```http
POST /api/v1/auth/login
```

Этот endpoint выбран потому, что login может часто использоваться для перебора паролей и создавать лишнюю нагрузку на базу.

Алгоритм: Fixed Window Counter.

Хранилище счётчиков: Redis.

Лимит:

```text
10 запросов в минуту с одного IP
```

При превышении лимита API возвращает:

```http
429 Too Many Requests
```

Также возвращаются заголовки:

```text
X-RateLimit-Limit
X-RateLimit-Remaining
X-RateLimit-Reset
```

## 6. Проверка rate limiting

Для проверки отправлялись повторные запросы на login.

После превышения лимита сервер вернул:

```http
429 Too Many Requests
```

Ответ:

```json
{"error":"too many login attempts"}
```

Заголовки при этом показывали лимит, остаток запросов и время до сброса окна.

## 7. Что это даёт?

Кеширование уменьшает количество повторных запросов к PostgreSQL. Повторные запросы к поиску книг и выдачам пользователя могут обслуживаться из Redis.

Rate limiting защищает авторизацию от слишком частых запросов и снижает риск лишней нагрузки на базу.

Для мониторинга можно смотреть:

- время ответа API;
- количество запросов;
- количество `X-Cache: HIT` и `X-Cache: MISS`;
- cache hit rate;
- количество ответов `429`;
- нагрузку на PostgreSQL и Redis.

Формула cache hit rate:

```text
cache hit rate = hits / (hits + misses)
```
